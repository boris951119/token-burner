一、执行摘要

token-burner 在 v0.4（Alpha）完成从「代码补全助手」到「项目级多智能体交付系统」的关键跨越： 容器级安全沙箱（只读文件系统 / 无网络 / 非 root / 资源配额）、异步任务 API 与 SSE 实时事件流（4 路并发、任务状态落盘可恢复）、 双模式意图识别（System-1 快判 + System-2 全量评估，闲聊/基础类诉求不再消耗全量评估成本）、三档智能模型路由、 Embedding / 论点库 / _shared 三级缓存、VS Code 插件全流程闭环、六层成本护栏与全链路可审计。 上述组合能力在同类竞品中尚无完整对标——多数竞品强于单点交互体验，弱于成本治理与可审计交付。

三、v0.4 交付后的差异化定位

3.1 三条独有护城河

  • 成本确定性：唯一把「六层成本护栏 + 三级缓存 + 智能路由 + 节省量看板」作为一等公民的产品——竞品的成本控制普遍停留在订阅定价层面，缺少任务内的程序化闸门。
  • 可审计交付：模块级决策记录、接口契约门禁、修复轮数上限、成本报告全部落盘可回溯——直接对应企业采购的安全与审计诉求。
  • 过程质量工程：PM/双评审/收敛的「团队讨论」阶段在竞品中普遍缺失；该阶段把「需求→方案」的失配在写码前拦截，是交付质量的结构性保障。

3.2 相对短板（诚实盘点）

  • 交互顺滑度不及 Cursor（逐行补全/内联编辑是 Cursor 核心场景，token-burner 定位为项目级交付，二者互补而非替代）。
  • 云原生体验不及 Devin（全托管、零环境搭建）；token-burner 的本地/私有化定位是刻意的安全取舍。
  • 生态品牌与分发渠道弱于 GitHub Copilot。

五、结论

v0.4 交付后，token-burner 在「成本治理 × 可审计交付 × 项目级多智能体」三个维度形成结构性差异化， 与 Cursor（交互体验）、Devin（全托管云）、通义灵码（国内生态）不在同一正面战场。 v0.5 的 Researcher 与可视化能力将进一步拉开「过程可观测性」差距；主要竞争风险仍来自 GitHub/Cursor 生态位下沉（从补全向项目级任务演进）与 Devin 的降价扩张—— 应对策略是持续放大「本地私有化 + BYOK + 可审计」的企业侧不可替代性，并以 v0.5 智能化能力巩固先行者优势。
