# 架构分析：为什么总是突破不了分数（2026-10-04 凌晨，ZCode）

> 回答用户两问：产品距离合格还差多远？为什么总在"漏写/多写/忘了"？

## 一、结论（三句话）

1. **产品不是架构错误，是"拆开生成"的固有接缝没有被对冲**——历届 13+ 个 0 分全部死在模块与模块的接缝上，没有一次是"功能本身写错"。
2. 对冲手段已验证有效：**kernel 化**（程序生成高危代码段）消灭了三类接缝病（DB 符号/schema 漂移/种子分裂），今晚补上第四类（UI 模块缺失守卫）。
3. 距离：**能稳定拿分差 1-2 周**（场景级验证进交付闸已在跑但覆盖不足）；**演示级已达标**（本地 86/86·176/219）；**企业可用差一个量级**（需求获取/迭代/部署，另一道题）。

## 二、"漏写/多写/忘了"的统一病理解释

| 用户观察 | 实际病灶（全部有 run 实锤） |
|---|---|
| 漏写 | 模块 A 以为 B 会做（种子账号只在业务模块、get_db 没人提供、DDL 少一列） |
| 多写 | 两个模块各做一遍（Sign in×2）——部分是**我们自己的修复指令逼出来的** |
| 忘了 | spec→模块→代码各层信息丢失，且**拼装后的完整旅程从没人走过一遍** |

提示词管不住的原因：接缝规矩数随模块数**平方增长**，提示词只覆盖其中大部分——每跑一次模型随机违反一条。这就是"修一个洞冒一个洞"的数学本质。

## 三、裁决：保留模块化架构 + 两块配套（而非推倒重来）

**为什么不立刻换单块生成**：单块（monolith）结构上无接缝，但整应用代码一次生成的输出体积可能超模型单次响应上限（12k tokens），质量风险未验证——这是**假设**不是结论。已做成实验开关（`module_mode=monolith`，config 缺省 modular 零行为），白天用同题对照跑裁决。

**配套一（接缝确定性保证，kernel 化）**——已有 4 个：

| kernel | 消灭的病 | 实证 |
|---|---|---|
| db_kernel | 39 模块死磕共享符号烧 2M | sheet_p0 后未复发 |
| auth_seed_kernel | 种子账号分裂→登录 401 全灭 | v63 四 run 日志已确认落盘 |
| [seed] 登录探测闸 | 官方登录 401 交付前不可见 | 单测+本地复现验证 |
| **UI 模块守卫（今晚新增）** | 拆分全 API 化→整树零 HTML | v61 病根，7 新测试 |

剩余候选 kernel 类（按风险序）：导航一致性（页间链接对账）、表单接线（action→路由→POST 处理三段对账——已有表单闸可升格）、会话传递（登录态跨页）。

**配套二（拼装后的整体验证）**：自测闸（LLM 从题面生成 Playwright 场景→真浏览器→失败进修复环）**已在主流程**，缺口是覆盖率与稳健性（v63 stage-1 覆盖 12/17 节点）。方向不是新建，是把生成成功率与"登录态场景"占比提上去。
